## https://developer.nvidia.com/nim

- **caution** 2026-08-07 (self-hosted NIM container, 49B model in FP8 on H100): The HTTP layer accepts requests and /v1/models answers before the vLLM backend is ready, so a health check passes while calls return 502. Startup runs load, autotune, CUDA graph capture, then app start. Wait for the Application startup complete log line, not for the port. A 30s wait was insufficient; 120s was reliable. - 502 Bad Gateway from the proxy after the container reported ready
- **caution** 2026-08-07 (self-hosted NIM, OpenAI-compatible endpoint): Model names are namespaced and the bare name 404s. Query /v1/models to discover the served id rather than assuming the catalog name. - the model X does not exist error against a name taken from the model card
- **caution** 2026-08-07 (2x 95GB datacenter GPUs, TP=2 PP=1 versus single-device): A 49B model in FP8 failed under tensor parallelism across two GPUs: illegal memory access and a hang during CUDA graph capture, after the weights had loaded. The same model on a single GPU was stable, with ~95GB VRAM ample for 49B at FP8. Quantized models do not automatically benefit from tensor parallelism; the synchronisation cost can exceed the capacity gain when one card already fits the weights. - CUDA error illegal memory access during graph capture; resolved by pinning to one device
- **works** 2026-08-07 (self-hosted NIM pull under free Developer Program membership): The NGC API key can be passed as a container environment variable, so no interactive registry login is needed. Separate from the key, each specific model requires a one-time in-browser terms acceptance on its catalog page before it can be pulled. That gate is per model, not per account, and is the easiest prerequisite to miss. - authentication failure on first pull, resolved by the per-model acceptance

## https://github.com/NVIDIA/NeMo-Agent-Toolkit

- **caution** 2026-08-07 (nvidia-nat 1.8.0, Python 3.13, uv resolver): nvidia-nat is a meta-package whose pip metadata carries no real version constraints; the actual pins live in nvidia-nat-core and nvidia-nat-langchain. Diagnosing a dependency conflict against the top-level package shows nothing. - direct PyPI metadata query; the resolver proof output was misleading on the same conflict
- **works** 2026-08-07 (nvidia-nat 1.8.0, agent emitting a JSON object with a disposition field): nat eval scoring a structured JSON output needs a custom BaseEvaluator subclass. The bundled openevals exact_match compares a whole response string and cannot address one field of a structured output. - first eval run scored 2 of 3 fixtures and surfaced a real behavioural gap rather than a wiring bug
- **caution** 2026-08-07 (nvidia-nat 1.8.0, develop branch): No native Anthropic LLM provider. nvidia-nat-core registers eight: aws_bedrock, azure_openai, dynamo, huggingface, huggingface_inference, litellm, nim, openai. Claude routes through _type litellm. At least one third-party blog claims native Anthropic support; the source tree and the official provider list both contradict it. - packages/nvidia_nat_core/src/nat/llm/register.py import list
- **works** 2026-08-07 (nvidia-nat 1.8.0): The profiler is not a separate CLI verb. It runs as part of nat eval when profiler settings are present under the eval.general.profiler config key, emitting latency percentiles, raw traces and token counts. A LangGraph agent registers as a real NAT function via a nat.components entry point, and the zero-code langgraph_wrapper workflow type also works. - docs/source/improve-workflows/profiler.md and a working registration

## https://github.com/nv-morpheus/Morpheus

- **caution** 2026-08-07 (Morpheus 25.06 runtime container, tabular flow features): Morpheus supplies the pipeline framework, not a model that fits arbitrary tabular data. No bundled model suits network flow features: ABP is supervised XGBoost over GPU telemetry for crypto-mining, and DFP is a per-entity autoencoder needing roughly 300+ records per entity. There is no generic unsupervised tabular anomaly stage in 25.06. The documented extension point is a custom SinglePortStage with PassThruTypeMixin wrapping your own model, which works well. - checked against the bundled model set and the stage API docs
- **caution** 2026-08-07 (Morpheus 25.06, multi-MessageMeta pipeline): WriteToFileStage with PARQUET is correct for exactly one message and corrupts silently for more. The file is opened once in wb and each message writes a complete parquet file into the same handle, so independent files with their own footers concatenate into one stream. Readers return only the first and nothing raises. Use CSV for any multi-message sink and convert once at the end. - downstream row counts silently short; single-message runs looked correct
- **caution** 2026-08-07 (Morpheus 25.06): A pipeline is one-shot. Pipeline.build asserts it can only be built once and run builds internally, so repeated runs need a fresh pipeline object each time. A Config is reusable across them. For a long-lived stream write a custom source stage with make_source yielding while the subscription is live; InMemorySourceStage binds a fixed list at construction and there is no API to push into a running pipeline. - Pipeline can only be built once assertion
- **caution** 2026-08-07 (Morpheus 25.06 runtime container, RAPIDS 25.02): The runtime container ships cuDF but no cuML, by design rather than oversight. Install cuML with conda pinned to the exact matching RAPIDS version; pip install of the CUDA-suffixed wheel pulls its own cuDF and overwrites the one the framework depends on. Also: docker exec does not run the image entrypoint, so no conda environment is activated and the default interpreter is the empty base env. Name the environment interpreter explicitly. - ModuleNotFoundError for cudf immediately after a successful install

## https://github.com/rapidsai/cuml

- **caution** 2026-08-07 (cuML 25.02): No IsolationForest implementation; the request issue has been open since 2021. For unsupervised anomaly work the GPU-native substitutes are NearestNeighbors distance, DBSCAN or HDBSCAN. Do not plan around an algorithm that is not there. - API surface and the open feature request
- **works** 2026-08-07 (RAPIDS 25.02 on a 95GB datacenter GPU, 16M-row tabular workload): cuDF parquet round-trips return float64. Cast to float32 before a large distance computation; a brute-force KNN is memory-bandwidth-bound and the cast roughly halves runtime at no accuracy cost for these magnitudes. Cleaning and engineering 16M rows across 10 CSVs ran in about 30 seconds on one datacenter GPU. - measured wall clock across the corpus
- **caution** 2026-08-07 (RAPIDS 25.02, NVIDIA driver 5xx series): Numba-backed GPU array interop needs NUMBA_CUDA_USE_NVIDIA_BINDING=1 on recent drivers. Without it the legacy ctypes binding enumerates zero devices and raises IndexError deep in device selection, or segfaults in the driver one frame earlier. numba.cuda.is_available() returns True regardless, because it only confirms the driver library loaded rather than that any device was enumerated, which makes this slow to diagnose. cuDF and CuPy are unaffected since they reach the driver through cuda-python, but every cudf .values or to_cupy call routes through the numba path. - IndexError in numba_cuda devices.py on a device list that was empty while is_available reported True
- **works** 2026-08-07 (RAPIDS ecosystem and downstream NVIDIA projects): RAPIDS and the NVIDIA projects built on it version as CalVer YY.MM rather than semver, so 25.02 is the February 2025 release and 25.06 the June one. Two consequences: the version string states its own age, so staleness is readable without a changelog; and components must be pinned to the same YY.MM across a stack, since a mismatched pair is a version conflict rather than a compatible upgrade. - observed pinning requirement between a framework container and a layered library
