# Spec: agent-mail skill

## Objective

Let independent Claude Code agents communicate by dropping **templated markdown
messages** into each other's agent-tooling inbox (`<agent-root>/inbox/`). One file
per message, write-once, human- and agent-readable. No daemon, no network, no
shared mutable state - just files on disk.

**Agent root.** The mailbox lives inside whichever agent-tooling folder the target
repo uses, one of `{.claude, .agents, .cursor}`. The root is resolved per send (see
*Root Resolution* below), never hard-coded - so the skill works for Claude, Cursor,
or `.agents`-convention repos alike.

**Users:** agents working in separate repos/worktrees that need to hand off
work, request something, acknowledge, or post an FYI to a peer agent.

**Success looks like:**
- An agent can send a message to a peer by pointing at the peer's **repo path**;
  the message arrives as one `.md` file in that repo's `<agent-root>/inbox/`.
- An agent can list its own unread inbox, read a message, act, and mark it
  `in-progress` / `resolved` / `canceled`, with resolved/canceled items moved
  into a flat `inbox/processed/` (messages are self-dating via their id).
- Acknowledgement is expressed by the `reply-needed` flag + the `status` tag;
  no separate receipt files.
- The send guard never silently creates infrastructure in someone else's repo,
  and never *guesses* which agent root to use when more than one is present.

## Tech Stack

- POSIX-ish **bash** scripts (`set -euo pipefail`), darwin/BSD userland.
- No `jq` (no JSON); envelopes are YAML front matter generated by the scripts.
- Distributed as a Claude Code **user-level skill** at `~/.agents/skills/agent-mail/`
  (`~/.claude/skills` symlinks there - see [[skills-dir-symlink]]).

## Commands

```
# Send a message (agent supplies body in a file)
bash ~/.agents/skills/agent-mail/scripts/send.sh \
  --to-repo /abs/path/to/peer/repo \
  --from BlueLake --from-repo "$PWD" \
  --to GreenCastle \
  --subject "auth refactor" \
  --type request --reply-needed \
  --body-file /tmp/body.md
  # add --root .claude|.agents|.cursor to disambiguate when several roots exist
  # add --create-inbox only after the user approves creating a new inbox

# Inspect a repo's agent roots (what exists, contents, recency) - used to
# present the choice to the user when more than one root is detected
# (shares the same report code path AMBIGUOUS_ROOT auto-prints)
bash ~/.agents/skills/agent-mail/scripts/send.sh --to-repo /path --inspect

# List my unread inbox (top-level <agent-root>/inbox/*.md)
bash ~/.agents/skills/agent-mail/scripts/inbox.sh [--repo .] [--root .claude] [--all]

# Update a message's status (and file it when resolved/canceled)
bash ~/.agents/skills/agent-mail/scripts/mark.sh \
  --file .claude/inbox/20260624100000-001__auth-refactor.md \
  --status resolved        # unread|in-progress|resolved|canceled

# Run the test suite (temp repos, no real inboxes touched)
bash ~/.agents/skills/agent-mail/tests/run.sh
```

## Message Format

One markdown file. **Filename** = `<message-id>__<slug>.md`, e.g.
`20260624100000-001__auth-refactor.md`. **Envelope** = YAML front matter:

```markdown
---
v: 1                               # envelope schema version
message-id: 20260624100000-001     # YYYYMMDDHHMMSS-NNN (UTC); matches filename prefix
in-reply-to: ""                    # message-id being replied to ("" if new); threads via this chain
date: 2026-06-24T10:00:00Z         # ISO-8601 UTC
from: BlueLake                     # sender agent name
from-repo: /abs/path/to/sender     # so the recipient can route a reply back (re-resolved at reply time)
to: [GreenCastle]                  # recipient agent name(s)
subject: "auth refactor"           # YAML-escaped; control chars / quotes / --- rejected or quoted
type: request                      # request | response | handoff | fyi
reply-needed: true                 # ack mechanism: sender expects a reply (must be false on type: response)
status: unread                     # unread | in-progress | resolved | canceled
---

<body rendered from templates/<type>.md>
```

Fields cut from v1 (reconstructable or unused): `thread-id` (walk `in-reply-to`),
`cc`, `priority`, `from-root` (re-resolved on reply, never trusted stale).

**message-id generation (race-safe):** id = `YYYYMMDDHHMMSS` (UTC) + `-NNN`. To pick
NNN, seed from a scan of the inbox (top level + `processed/`) for that second, then
**create the file atomically** with `O_EXCL` semantics (`set -o noclobber`, redirect
to a temp name, `mv` into the final `<id>__<slug>.md`). On a losing race the create
fails → increment NNN and retry. The pre-scan is only a hint; correctness comes from
the atomic create, so concurrent same-second sends never clobber each other.

**Ack / acknowledgement:** the sender sets `reply-needed: true`. The recipient
acknowledges by (a) updating `status` on the delivered file, and (b) when a reply
is needed, sending a `type: response` message back to `from-repo` (root re-resolved
at reply time), carrying `in-reply-to: <original message-id>`. A `type: response`
must carry `reply-needed: false` to prevent reply ping-pong.

## Concurrency & Safety (load-bearing - these are correctness, not polish)

- **Atomic writes.** Never write a message or edit a status in place where a reader
  could observe a partial file. Write to `inbox/.tmp.<rand>` and `mv` into the final
  name (rename is atomic on one filesystem). Status edits: render the updated file to
  a temp, then `mv` over the original.
- **Race-safe ids** via atomic create + retry (see *message-id generation*). The
  "unique filename" guarantee comes from the create, never from a pre-scan.
- **YAML escaping.** `subject` (and any agent-supplied envelope string) is escaped
  per YAML rules - double-quote + escape, reject embedded newlines / control chars /
  a literal `---`. Never raw-interpolate user text into the front matter. Body text
  lives below the `---` fence and is not interpolated into YAML.
- **Path safety.** `realpath -P` canonicalize `--to-repo` and the resolved root;
  refuse a symlinked agent root (or follow then re-validate); verify the resolved
  `inbox/` stays under the resolved repo before any write. Reject `..` traversal.
- **Ownership.** Once delivered, a message is **recipient-owned**: the sender never
  rewrites it. There is no `--force`/overwrite of a delivered file - atomic create +
  retry guarantees a fresh id instead.
- **BSD userland (darwin).** Pin BSD syntax in `lib.sh`: `stat -f %m`, `date -u`,
  and **`awk` (not `sed -i`)** for front-matter edits. No GNU-only flags.
- **Delivery semantics.** Best-effort, at-most-once, same-machine. Send exiting 0
  means "file written," not "recipient saw it"; the boot-rule inbox scan is how
  messages get noticed. State this in SKILL.md and the guide.

## Root Resolution (pre-flight, runs before anything is written)

Before any delivery, resolve which agent root the target repo uses. Detect which
of `{.claude, .agents, .cursor}` exist as directories at the repo top level:

- **`--root <name>` given** → use it; error `ROOT_NOT_PRESENT` (exit 8) if that
  folder doesn't exist in the repo.
- **none detected** → `NOT_AGENT_REPO` (exit 6): the target isn't an agent
  workspace. **Back off and talk to the user** - do not create anything.
- **exactly one detected** → that is the agent root; proceed.
- **more than one detected** → `AMBIGUOUS_ROOT` (exit 7): **do not guess.** Emit a
  report and stop; the user picks, then the agent reruns with `--root`.

**Ambiguity report (`--inspect`, also auto-printed on `AMBIGUOUS_ROOT`).** For
every detected root, report enough for the user to choose:
- the folder name and whether it already contains an `inbox/`;
- a content summary (file/subdir count, and whether mail is present);
- **recency** (a *weak hint*, not ground truth - git/cp/rsync rewrite mtimes): the
  folder's last-modified time and the newest file inside it (path + mtime), to help
  the user judge which tooling is actually in use.

This satisfies "if more than one exists, go back to the user and say which folders
are populated, with what, and how recently each (and its files) changed."

## Delivery Guard Flow (send.sh)

Resolve `--to-repo`, run **Root Resolution** (above) to get `<agent-root>`, then:

| Condition | Exit | Script prints | Agent does |
|---|---|---|---|
| repo path missing | 2 | `REPO_NOT_FOUND` | report to user |
| none of `.claude/`,`.agents/`,`.cursor/` | 6 | `NOT_AGENT_REPO` | **back off, talk to user** |
| more than one root present | 7 | `AMBIGUOUS_ROOT` + report | **show report, ask user to choose**; rerun with `--root` |
| `--root` names an absent folder | 8 | `ROOT_NOT_PRESENT` | report to user |
| `<agent-root>/` present but no `inbox/` | 4 | `NO_INBOX` | **ask user:** "Sure you want to start communicating with {repo} via `<agent-root>/inbox/`?" → on yes, rerun with `--create-inbox` |
| ok | 0 | written path | report delivered |

(There is no `FILE_EXISTS`/`--force` path: atomic create + NNN retry guarantees a
unique id, and delivered files are recipient-owned and never overwritten.)

`--create-inbox` is the *only* way the script creates an `inbox/` in another repo,
and the agent only passes it after explicit user approval. The script **never
creates an agent root** (`.claude`/`.agents`/`.cursor`) itself - only an `inbox/`
inside one that already exists.

## Read / Status / Archiving (mark.sh)

- **unread:** lives at top-level `inbox/*.md`.
- **in-progress:** stays at top level; `status:` tag updated (atomic temp + `mv`).
- **resolved | canceled:** `status:` updated, then file **moved** to a flat
  `inbox/processed/`. The message is self-dating (id + `date:`), so no date buckets.
- Status writes target the front matter of the **delivered** file (recipient-owned,
  safe to edit) via atomic temp-then-`mv`. A message whose front matter is malformed
  is surfaced as an **error**, not silently papered over - there is no sidecar.

## First-Contact / Onboarding

A recipient agent may have **never used agent-mail** and may not even have the
skill installed. The system must be self-bootstrapping: the inbox explains itself.

**1. The inbox is self-describing.** Whenever an inbox is created (the
`--create-inbox` path in send.sh), the script also writes
`inbox/HOW-TO-AGENT-MAIL.md` - a plain-language guide that requires no prior
knowledge and no tooling. It covers:
- what these `.md` files are and that each one is a message addressed to you;
- the envelope fields and what `status` / `reply-needed` / `in-reply-to` /
  `from-repo` mean;
- **how to read:** look at top-level `inbox/*.md` (those are unread); read oldest
  `message-id` first;
- **how to act + track:** set `status:` to `in-progress`, then `resolved` or
  `canceled` when done;
- **how to reply** when `reply-needed: true`: send a `type: response` message back
  to the sender's `from-repo`, carrying `in-reply-to: <original message-id>` (and
  `reply-needed: false`);
- **how to file** a finished message: move it to `inbox/processed/`;
- a **no-tooling fallback**: exact `mv` + front-matter-edit steps to read, mark,
  reply, and file entirely by hand if the agent-mail scripts aren't available,
  plus the one-line install pointer for the skill.

**2. SKILL.md teaches the receiving half, not just sending.** It includes a
"Receiving mail" section (discover → read → act → status → reply → file) and a
**boot rule**: at session start, and whenever the user mentions inbox/mail/peer
agents, check each present agent root (`.claude`/`.agents`/`.cursor`) for an
`inbox/` and surface a one-line summary of top-level unread `*.md` (count +
subjects). No `inbox/` or no top-level files means no unread mail.

**3. Enabling yourself to receive.** To let peers message you, you need an
`<agent-root>/inbox/`. The guide and SKILL.md both note this; an agent can create
its own inbox directly (it owns its repo) - the `--create-inbox` *guard* only
governs creating one in **someone else's** repo.

## Code Style

Mirror the existing `~/.claude/hooks/*.sh` style: `#!/usr/bin/env bash`, a header
comment block explaining intent, `set -euo pipefail`, small focused functions in
`lib.sh`. Example:

```bash
#!/usr/bin/env bash
# send.sh - deliver one markdown message into a peer repo's <agent-root>/inbox/.
set -euo pipefail
source "$(dirname "$0")/lib.sh"

# Atomic, race-safe create: seed NNN from a scan, then let O_EXCL settle ties.
deliver() {            # $1 = inbox dir, $2 = slug, $3 = tmpfile → echoes final path
  local ts seq dest; ts=$(date -u +%Y%m%d%H%M%S); seq=$(seed_seq "$1" "$ts")
  while :; do
    dest="$1/$(printf '%s-%03d' "$ts" "$seq")__$2.md"
    if ( set -o noclobber; mv -n "$3" "$dest" ) 2>/dev/null && [ -e "$dest" ]; then
      printf '%s\n' "$dest"; return 0
    fi
    seq=$((seq + 1))   # lost the race → next NNN
  done
}
```

## Testing Strategy

`tests/run.sh` creates throwaway repos under a temp dir (never a real agent root)
and asserts:
- root resolution: no agent folder → `NOT_AGENT_REPO`; exactly one (`.cursor` or
  `.agents` or `.claude`) → auto-selected; two+ → `AMBIGUOUS_ROOT` and the report
  names each folder with contents + recency; `--root` selects, and an absent named
  root → `ROOT_NOT_PRESENT`;
- each remaining guard branch returns the right exit code + token (REPO_NOT_FOUND,
  NO_INBOX, success);
- `--create-inbox` creates `inbox/` inside the chosen root (never creates the root
  itself) and delivers;
- delivered file has a well-formed envelope; filename prefix == `message-id`;
- **race safety:** two deliveries forced to the same `YYYYMMDDHHMMSS` produce two
  distinct files (NNN differs); neither is lost;
- **YAML safety:** a subject containing `"`, a newline, and `---` yields a still-
  parseable envelope (or is rejected) - never a corrupt file;
- **path safety:** a `--to-repo` with `..` or a symlinked root is refused / resolved
  and re-validated; no write escapes the repo;
- `mark.sh` updates `status` (atomic) and moves resolved/canceled files into flat
  `inbox/processed/`; a malformed front matter surfaces an error (no sidecar).
Verification = `tests/run.sh` exits 0 with all assertions green.

## Boundaries

- **Always:** resolve the agent root before writing; write atomically (temp + `mv`);
  one file per message with message-id == filename prefix; YAML-escape agent-supplied
  strings; canonicalize paths before any write; drop `HOW-TO-AGENT-MAIL.md` into any
  inbox at creation time; run `tests/run.sh` before declaring done.
- **Ask first:** creating an `inbox/` in a repo that has none; choosing a root when
  more than one is present (show the recency/contents report); sending to a repo the
  user hasn't named.
- **Never:** create an agent root (`.claude`/`.agents`/`.cursor`) in another repo;
  write into a repo with none of those folders; guess a root when several exist;
  overwrite a delivered (recipient-owned) message; raw-interpolate user text into
  YAML; broadcast (no recipient = no send).

## Success Criteria

1. `tests/run.sh` passes all assertions.
2. A real send into a peer repo with `.claude/inbox/` produces a correctly-named,
   well-formed message file and exits 0.
3. Sending to a repo with none of `.claude/`,`.agents/`,`.cursor/` exits
   `NOT_AGENT_REPO` and writes nothing.
3a. Sending to a repo with more than one agent root exits `AMBIGUOUS_ROOT`, writes
   nothing, and prints a report naming each root with its contents + recency;
   `--root` then selects one.
4. Sending to a repo whose resolved root has no `inbox/` exits `NO_INBOX` and writes
   nothing until `--create-inbox` is passed.
5. `mark.sh --status resolved` moves the file to flat `inbox/processed/` with
   `status: resolved`, written atomically.
6. SKILL.md triggers on relevant phrasing ("message/notify/hand off to agent X",
   "send to inbox", "check my inbox").
7. A newly created inbox contains `HOW-TO-AGENT-MAIL.md`, and a first-time agent
   with **no prior knowledge and no scripts** can follow it to read, mark, reply,
   and file a message by hand.

## Open Questions

- Agent identity (`--from` name): default to repo basename if not given? (assumed yes)
- Should `inbox.sh` also surface messages in `processed/` by default? (assumed no;
  `--all` opts in)
- Long-term retention: any cap on flat `processed/` size, or leave pruning manual?
  (assumed manual for v1)
- Root resolution is decided: none → fail; one → auto; many → ask user with a
  contents+recency report and require `--root`. The mailbox lives in the chosen
  root's `inbox/`; the skill never creates the root itself.
